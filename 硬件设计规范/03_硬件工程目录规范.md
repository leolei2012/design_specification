## 1. 目的与适用原则

使项目成员能够快速找到设计输入、有效源文件、验证证据和已批准交付物；使接手人员能够恢复工程，使生产方能够明确使用哪个发布包。

本文的目录、命名及流程为团队建议约定，不是EDA软件或行业标准强制要求。软件自带的工程组织、路径引用及库管理机制优先满足；迁移目录前应验证工程能够正常打开和生成输出。

- **必须**：发布前满足；偏离时保留原因、风险、验证证据和批准记录。
- **应**：默认执行，不采用时说明理由。
- **建议**：按项目规模选用，不为满足目录形式创建无用途文件。

## 2. 工程边界与组织层级

| 编号 | 等级 | 规则及检查依据 |
|---|---|---|
| ORG-01 | 必须 | 明确产品、板卡、板卡硬件版本、装配变体和发布批次的关系；不得用同一个“版本号”混指全部对象。 |
| ORG-02 | 应 | 一个仓库管理一个产品或一组需要协同发布的板卡；独立维护、权限或生命周期明显不同的板卡可独立建仓库。 |
| ORG-03 | 必须 | 每块板卡有唯一板卡标识和明确的主工程入口；同一版本不得存在多个无法判定有效性的源文件副本。 |
| ORG-04 | 应 | 普通设计修订通过版本控制记录；不按每次修改复制整个工程目录。需要并行维护的硬件大版本可使用维护分支，独立工程或目录必须声明维护关系。 |
| ORG-05 | 必须 | 机械、固件及软件若在其他仓库维护，在接口说明或项目首页记录对应版本、路径或受控链接，避免无版本地复制文件。 |

单板项目采用第3章结构即可。多板产品建议使用产品级目录：

```text
<PRODUCT_ID>/
├── README.md                 # 产品说明、板卡清单、仓库导航
├── system/                   # 系统架构、电源与跨板接口、集成验证
└── boards/
    ├── <BOARD_A>/            # 每块板采用第3章结构
    └── <BOARD_B>/
```

产品共用的接口文件保留一个受控来源；板卡文档引用其版本。跨板联合发布时，产品发布清单必须列出各板卡发布编号及兼容的固件、线缆和结构版本。

## 3. 推荐的单板工程目录

以下为完整参考结构。小项目可省略无内容的可选目录，但保留实际采用目录的含义。目录名推荐使用英文小写、数字和下划线，以便脚本及跨平台工具处理；文档正文可使用中文。

```text
<BOARD_ID>/
├── README.md                     # 工程入口、版本关系、工具和恢复方法
├── CHANGELOG.md                  # 已发布版本的重要变化
├── .gitignore                    # 按实际EDA工具配置，禁止忽略必要源文件
├── 01_requirements/              # 需求、环境条件、电气指标、设计输入
├── 02_architecture/              # 框图、电源树、接口与关键方案
├── 03_design/                    # 唯一有效的EDA设计源文件
│   ├── <native_project_files>    # 按工具要求组织项目、原理图及PCB
│   ├── libraries/                # 项目专用库或可恢复的依赖快照（按需）
│   └── constraints/              # 外部规则、叠层、阻抗与时序约束（按需）
├── 04_analysis/                  # 计算、仿真、模型及结果说明
├── 05_mechanical/                # 结构输入、板框、限高、装配接口与核对
├── 06_verification/              # 测试计划、调试、测量及验证结论
│   ├── plans/
│   └── runs/                    # 按测试批次保存原始数据与报告
├── 07_reviews/                   # 原理图、布局、布线、制造及发布评审
├── 08_manufacturing/             # 制造/装配约定、工艺要求、供应方确认
├── 09_releases/                  # 经批准的交付基线；禁止原地覆盖
│   └── <RELEASE_ID>/
├── references/                   # 有权保存的参考资料与来源索引（按需）
├── tools/                        # 输出、校验及辅助脚本（按需）
└── work/                         # 本地临时输出与缓存，不作为交付依据
```

### 3.1 设计源文件的组织

不强制将原理图和PCB分别放入子目录。Altium、KiCad及其他工具应使用其支持的项目结构，保留全部必要的项目配置、原理图、PCB、规则及库引用文件；禁止只提交单个PCB文件就认为工程完整。

工具将规则、叠层或输出任务保存在原生工程内部时，以工程内部数据为准，不要求重复导出到 `constraints/`。额外导出的说明必须注明对应源版本及用途。

### 3.2 各类文件的归属

| 文件或信息 | 受控位置 | 管理要求 |
|---|---|---|
| 需求、接口定义与电源树 | `01_requirements/`、`02_architecture/` | 记录输入版本、批准状态及未决项 |
| 原理图、PCB、项目配置与项目专用库 | `03_design/` | 是设计修改的有效来源，能够恢复引用关系 |
| 原理图中维护的器件属性、料号及DNP | 原生工程或声明的受控物料系统 | 明确BOM生成来源，禁止维护两个互相冲突的主BOM |
| 计算与仿真 | `04_analysis/` | 保存输入、单位、假设、工具版本及结论；必要模型可恢复 |
| STEP、DXF及结构输入 | `05_mechanical/` | 区分外部输入与本工程导出，注明来源、版本及坐标基准 |
| 测试记录 | `06_verification/runs/` | 关联板卡版本、样机编号、固件、仪器、条件及原始数据 |
| 评审、问题和偏离记录 | `07_reviews/` | 关联源版本、规则编号、负责人、证据及关闭状态 |
| 板厂/装配方能力与工艺确认 | `08_manufacturing/` | 记录供应方、适用项目、确认日期及采用版本 |
| 临时PDF、Gerber、BOM及试导出 | `work/` | 可重建；不发送为正式生产依据 |
| 已批准的生产交付文件 | `09_releases/<RELEASE_ID>/` 或受控制品库 | 固定内容，保留版本清单和完整性校验信息 |

## 4. 项目首页的最低内容

`README.md` 应使首次接手人员无需猜测即可打开有效工程，至少包含：

1. 产品名、板卡标识、用途、负责人及当前状态。
2. 主工程文件的相对路径，以及EDA软件、版本、必要插件。
3. 器件库、封装库、3D模型及其他外部依赖的恢复方法和版本。
4. 硬件修订、装配变体、发布编号和固件兼容关系的说明。
5. 目录导航、原理图及PCB规范、接口定义和评审记录的位置。
6. 工程打开、ERC/DRC、输出生成及发布检查的方法；脚本注明运行目录。
7. 最近批准的发布编号及交付物位置，不用“最新文件”作为唯一定位方式。

示例：

```text
板卡：CTRL01，低压控制板
设计版本：硬件V1.2；当前分支为开发中内容
主工程：03_design/CTRL01.kicad_pro
工具：填写已验证的具体版本及必要插件
依赖：填写项目库路径、共享库版本及恢复方式
发布：CTRL01_HW-V1.2_ASM-STD_R01
兼容：填写已验证的固件、结构与接口版本
检查：填写ERC、DRC、评审及制造输出复核入口
```

## 5. 命名与版本标识

| 编号 | 等级 | 规则及检查依据 |
|---|---|---|
| NAME-01 | 必须 | 板卡标识在产品范围内唯一，并用于工程首页、BOM、图纸、发布清单和相关记录。 |
| NAME-02 | 应 | 受工具或脚本处理的路径避免空格及系统保留字符；同一路径不能只靠大小写区分文件，避免跨平台冲突。 |
| NAME-03 | 必须 | 保留原生扩展名及软件要求的关联文件名；不得为满足通用命名格式而破坏项目配对、库引用或脚本。 |
| NAME-04 | 应 | 受控导出文件使用“板卡标识_内容_版本”命名，例如 `CTRL01_Schematic_HW-V1.2.pdf`；日期用于记录批次，不能单独替代版本。 |
| NAME-05 | 必须 | 禁止用“最终版”“最新版”“最终版2”等名称识别正式交付；历史发布通过唯一发布编号定位。 |
| NAME-06 | 必须 | 硬件修订策略在项目中声明。改变裸板设计并需要区分实物时更新硬件修订；只改变贴装选项时更新装配变体或其版本。 |
| NAME-07 | 必须 | 同一硬件修订重新发布时使用新的发布序号并说明原因；发现影响电气、结构或制造的设计修改，按项目策略重新判定硬件修订，不以发布序号代替。 |

推荐的发布编号为：`<BOARD_ID>_HW-<硬件版本>_ASM-<装配变体>_R<发布序号>`。

例如 `CTRL01_HW-V1.2_ASM-STD_R01`。其中 `STD` 是项目定义的标准装配选项；变体定义发生变化时，还需记录其受控版本。裸板由多个变体共用时，可共用制造主数据，但发布清单必须明确其对应关系，不能混用BOM或坐标文件。

## 6. 依赖、路径与跨机器恢复

| 编号 | 等级 | 规则及检查依据 |
|---|---|---|
| DEP-01 | 必须 | 工程依赖的符号、封装、3D模型、字体、仿真模型和插件应能按记录恢复；禁止仅依赖某人的桌面目录或个人网盘。 |
| DEP-02 | 应 | 使用工程相对路径或软件支持的项目变量；机器级路径变量在首页说明配置方法，不保存个人绝对路径作为唯一引用。 |
| DEP-03 | 必须 | 共享库固定到可定位版本、提交或受控快照；只写“使用最新库”不能构成发布基线。 |
| DEP-04 | 必须 | 确认第三方资料及模型的保存和分发权限；不能随包分发的依赖记录授权获取方式和准确版本，并验证有权限的接手人员可获取。 |
| DEP-05 | 必须 | 发布前在新的检出目录或另一台合适机器验证工程恢复，覆盖打开工程、库解析、ERC/DRC及必要输出；记录工具版本和检查结果。 |

## 7. 版本控制与本地文件

源文件、必要项目配置、设计输入、评审记录和脚本应纳入版本控制或等效受控系统。二进制EDA文件难以自动合并时，应约定编辑负责人或使用受支持的锁定机制；发生冲突后必须在EDA工具中复核，不直接采用文本合并结果作为正确性证据。

| 类别 | 处理方式 |
|---|---|
| 原生工程与必要配置 | 纳入版本控制；先辨认文件用途，再决定是否忽略 |
| 自动保存、锁文件、缓存及本地界面状态 | 经确认不影响恢复后忽略；不直接套用未知忽略规则 |
| 临时输出和个人试验 | 放入 `work/` 或工具支持的本地路径，按项目规则忽略 |
| 大型模型、测量数据和发布包 | 可使用Git LFS或受控制品库；保留版本、获取方式与校验信息，并验证实际文件可获取 |
| 密码、令牌、许可证密钥和个人账户信息 | 不进入仓库或发布包，使用团队批准的安全配置方式 |

Git标签用于定位发布源版本；标签及分支保护按平台能力配置。标签不能代替交付物存档，也不能证明发布包与该提交一致。

## 8. 发布目录与不可覆盖规则

正式发布前执行原理图规范第10章和PCB规范第14章的发布条件。`09_releases/` 只保留已批准内容，发布包准备过程在本地临时目录完成。

```text
09_releases/<RELEASE_ID>/
├── RELEASE.md               # 身份、源版本、工具、变体、批准及使用说明
├── manifest.csv             # 文件路径、用途、版本及适用范围
├── SHA256SUMS               # 包内交付文件的SHA-256，不包含自身
├── source/                  # 对应源快照，或受控归档及获取说明
├── schematic/               # 可检索原理图PDF
├── fabrication/             # 板厂接受的制造主数据、钻孔、制造说明
├── assembly/                # BOM、DNP、坐标、装配图及特殊工艺说明
├── mechanical/              # 交付所需的板框、尺寸、STEP等（按需）
└── evidence/                # ERC/DRC、评审、偏离及输出复核证据
```

| 编号 | 等级 | 规则及检查依据 |
|---|---|---|
| REL-01 | 必须 | `RELEASE.md` 记录板卡、硬件修订、装配变体及其版本、发布编号、时间、源提交或等效基线、工具及库版本、批准记录和适用范围。 |
| REL-02 | 必须 | 输出来自明确的源基线；不得夹带未记录的工作区修改。生成脚本及输出配置也须可定位。 |
| REL-03 | 必须 | 源归档包含恢复所需的实际依赖；使用子模块或LFS时不能只归档指针。源基线及后续加入的发布文件提交关系须说明，避免自引用。 |
| REL-04 | 必须 | 制造数据采用板厂接受的格式；多格式并存时指定唯一受控制造主数据，禁止让供应方猜测。 |
| REL-05 | 必须 | 生成后独立复核制造输出、BOM、坐标和装配变体；生成校验清单后验证所有列入文件，校验值只用于检测内容变化，不代表审批或设计正确。 |
| REL-06 | 必须 | 已发布目录和交付压缩包不得原地修改或覆盖；任何替换使用新发布编号，记录变更、重新检查并通知使用方。 |
| REL-07 | 必须 | 作废发布保留追溯记录，并在受控发布索引明确禁止使用及替代编号；不能只改文件夹名称或删除旧包来表示作废。 |
| REL-08 | 必须 | 对外只发送批准的发布包或受控链接，并记录接收方、发送时间和发布编号；单独散发文件时仍须能定位其批准基线。 |

发布包可存入受控制品库，而不把大型二进制文件全部提交Git。采用外部存储时，仓库保留发布索引、准确制品标识、获取方式、校验信息和批准记录；确认权限、备份及保留期限，禁止只依赖临时下载链接。

## 9. 日常使用与目录迁移

1. 建立工程时确定板卡标识、目录入口、工具版本和库管理方式，填写首页。
2. 修改设计时维护有效源文件，评审和测试记录指向实际检查的源版本；中间输出放入 `work/`。
3. 准备发布时关闭阻断问题，固定设计基线，生成并复核交付物，在批准后归档发布包。
4. 重新发布时建立新发布编号，保留旧记录，明确新旧版本的差异及适用关系。
5. 交接时按首页在新的检出目录恢复工程，并确认外部依赖和发布包均可获取。

现有工程迁移前先备份并记录源基线，检查脚本、库路径、输出任务和机械引用。小批移动后在EDA工具中验证，不能仅以文件复制成功判断迁移完成。历史发布包保持原样，新规范用于后续受控发布；需要补录历史索引时注明补录来源和未验证项。

### 11.1 乐鑫 ESP32-S3-LCD-EV-Board 官方实例

### 11.2 参考结论与团队自定部分

采用厂商公开实践的核心是：**按板卡区分资源、按文件类别组织交付、显式标识版本，并保留硬件修订与历史资料入口**。对于多个板卡及不同文件版本，使用发布清单记录实际匹配关系。

本文的 `01_requirements/` 至 `09_releases/` 目录名称、硬件/装配/发布编号格式、SHA-256清单、发布不可覆盖、评审审批和保存期限等为团队提出的管理要求，未声称由乐鑫官方强制规定。现有两份设计规范中的TI、ADI、ST及NXP资料用于电路与PCB技术检查，不将它们当作工程目录命名制度的证据。
