## 1. 目的、依据与规则等级

统一嵌入式软件的架构、目录、编码、构建、验证和发布要求，使模块可复用、工程可恢复、问题可追溯。

本文主要整理参考工程 `docs/规范/architecture.md` 和 `docs/规范/coding_standard.md`，并核对README、配置、入口、Keil工程及测试文件。架构和编码约定沿用原文；错误处理、并发、测试和发布等内容为补充要求。存在歧义的条款按本文说明澄清，不将参考工程当前实现的偏差作为规范。

- **必须**：项目发布前满足，偏离须记录原因、影响、验证措施及批准人。
- **应**：默认执行，不采用时说明理由。
- **建议**：按项目规模采用。

通用规则不绑定STM32、170 MHz或Keil。芯片、板卡、编译器、语言标准、SDK和运行环境在具体项目README中声明。第三方代码保持其原有风格及许可证，不对其强行套用第一方编码格式。

## 2. 软件分层与依赖

### 2.1 职责与允许依赖

```text
app              产品功能、业务状态机
 ↓
middleware       协议、监控、升级等公共能力（按需）
 ↓
drivers          具体设备及传感器语义
 ↓
hal              外设抽象、外设实例薄封装
 ↓
mcal             厂商SDK、CMSIS、HAL/LL等
```

向下箭头表示允许的依赖方向，不要求每次调用经过全部层。`app`应优先依赖设备或服务接口，必要时使用公开HAL抽象，不能直接访问寄存器或厂商HAL/LL接口。

| 目录 | 职责与边界 |
|---|---|
| `bsp/` | 横向板级支持：入口、时钟、引脚、有效电平、NVIC、启动及链接布局；可依赖mcal |
| `hal/` | 外设薄封装，可读取bsp板级配置并使用mcal，不处理产品业务 |
| `drivers/` | 设备行为、数据转换及设备状态；可读取bsp配置，硬件访问通过hal |
| `middleware/` | 按需增加的服务和协议，不反向依赖app |
| `app/` | 业务策略与产品状态机，不持有厂商外设句柄作为公共接口 |
| `utils/` | 通用算法、数据结构与工具；平台相关部分隔离为适配接口，不把所有工具都假定为纯主机代码 |
| `config/` | 功能开关、产品配置及固件版本的声明来源 |
| `third_party/` | 第三方代码、固定版本、来源及许可证 |
| `rtos/` | 选定内核及移植；未使用时允许仅保留说明 |

### 2.2 依赖约束

| 编号 | 等级 | 要求 |
|---|---|---|
| ARCH-01 | 必须 | 模块编译依赖保持有向无环，禁止用相互包含头文件或共享全局变量掩盖循环依赖。 |
| ARCH-02 | 必须 | drivers不得直接依赖mcal；app、middleware及可复用驱动的公开接口不得泄漏芯片寄存器类型。 |
| ARCH-03 | 应 | 可替换的设备、数据源和服务通过公开接口、ops或回调注入；模块不包含其他模块的私有头或 `.c` 文件。 |
| ARCH-04 | 必须 | 引脚、板级有效电平和时钟配置有单一受控来源；设备配置表可引用bsp定义，不在多个模块硬编码同一引脚。 |
| ARCH-05 | 应 | 换板优先只调整bsp及必要的hal；设备或产品需求同时变化时按实际影响修改，不宣称任意换板均无需改驱动或应用。 |

板级启动、中断分发和组合根属于框架接线点，可以引用其负责装配的模块公开接口。这是明确的集成职责，不允许普通底层模块借此调用上层业务。

出现循环依赖时，依次考虑提取公共低层模块、注入接口、事件/消息解耦或上提到组合根。回调的运行方向可以向上，底层仍只保存函数指针与上下文，不链接具体上层实现。

## 3. 工程目录与文件组织

沿用参考工程的“层 / 模块 / include、src”形式：

```text
<project>/
├── README.md
├── CHANGELOG.md
├── app/
│   ├── app.h
│   ├── app.c                       # 本层组合根
│   └── <module>/
│       ├── include/<module>.h
│       └── src/<module>.c
├── drivers/                        # 同app的模块组织方式
├── middleware/                     # 按需增加
├── hal/                            # 允许平铺hal_*.h/.c
├── bsp/
│   ├── include/
│   ├── src/                        # main、board、isr等
│   ├── startup/
│   └── linker/
├── config/
├── utils/<module>/{include,src}/
├── mcal/                           # 固定版本的厂商SDK
├── third_party/
├── rtos/
├── project/<toolchain>/            # IDE工程或构建配置
├── tests/                          # 主机单测、集成及板级测试
├── docs/                           # 规范、设计、硬件接口和验证记录
└── build/                          # 临时输出，可按工具调整
```

每个小模块从同名 `.h/.c` 开始，复杂模块可拆为多个私有实现文件，不为保持“一对文件”而堆积无关功能。对外只暴露 `include/`，私有头留在实现目录。

第一方头文件采用裸文件名包含，例如 `#include "drv_ain_sensor.h"`。各模块公开目录显式加入IncludePath，保证头文件名唯一；不将整个源码树递归加入包含路径。第三方库保留原有包含方式。

新增模块时须同时更新：公开接口、实现源文件、IncludePath、源文件列表、组合根接线、配置及相关测试。每个目标显式声明源文件，不以目录通配隐式加入测试、其他板卡或生成文件。

## 4. 对象、组合根与初始化

### 4.1 对象设计

- 第一方对象使用带tag的 `struct`，不为对象结构体定义 `_t` 别名；第三方及标准库类型保持原样。
- 方法使用“模块前缀 + 动作”，操作对象时 `self` 为第一个参数。
- 状态由对象持有；模块内部辅助函数和私有数据使用 `static`。
- 组合根持有实例并装配依赖；可复用模块不暗中创建单例。
- 只读板级配置使用 `static const` 或显式配置注入，避免为每个对象复制不必要的常量表。
- 初始化必须逐项建立有效状态；只在适合的普通数据结构上采用零初始化，不能假定全零字节适合所有第三方对象或资源。

### 4.2 组合根职责

各层 `<层>.c` 负责实例化、依赖注入和初始化编排；RTOS线程创建可分到 `<层>_task_init()`，业务逻辑放入模块。

原文“组合根零逻辑”在本文解释为**不承载业务判断和状态机**。必须允许检查初始化返回值、处理依赖失败和必要的资源回收；不能为了禁止 `if` 而忽略错误。

### 4.3 启动顺序

```text
板级早期初始化 → hal → drivers → middleware（如有）→ app
→ 验证依赖就绪 → 主循环或启动调度器
```

裸机在main显式调用；RT-Thread可使用已核对顺序的分级初始化；FreeRTOS、ThreadX等按实际内核规则创建对象并启动调度器。不照搬其他内核的自动初始化宏。

对象构造、外设初始化、线程创建和线程开始执行的时机必须明确。线程、定时器和中断不能在依赖尚未就绪时访问对象；失败后进入已定义的安全状态，不继续正常业务。

## 5. C语言编码约定

| 项目 | 约定 |
|---|---|
| 文件、函数 | 小写加下划线，函数采用模块前缀，例如 `drv_ain_sensor_poll` |
| 对象类型 | `struct app_alarm_system`；使用处保留struct关键字 |
| 文件静态变量 | `s_` 前缀，例如 `s_alarm_system` |
| 全局变量 | `g_` 前缀；优先只读或通过接口访问，不以全局可写表形成隐式依赖 |
| 局部变量 | 无作用域前缀，名称体现含义及必要单位 |
| 宏、枚举常量 | 大写下划线，公共枚举常量含模块前缀 |
| 缩进 | 4空格，不用Tab |
| 大括号 | Allman风格，左括号独占一行；单语句控制块也保留括号 |
| 空格 | 二元运算符两侧、关键字后及逗号后加空格 |
| 行长 | 尽量不超过100字符，必要时换行并保持清晰 |
| 注释 | 公开API采用Doxygen `/** ... */`；成员说明使用 `/**< ... */` |

### 5.1 头文件与接口

1. 使用唯一包含保护宏，头文件可独立包含，不依赖偶然的包含顺序。
2. 只包含必需头文件，指针类型可使用struct前向声明；不公开内部实现和厂商寄存器细节。
3. 接口说明参数范围、单位、缓冲区容量、所有权、有效期、返回值、执行上下文及是否阻塞。
4. 文件内部符号使用static，跨模块访问通过公开接口，不直接修改其他对象私有状态。

### 5.2 类型、常量和转换

- 位宽敏感数据使用 `<stdint.h>` 类型；长度和对象大小优先 `size_t`；`bool` 来自 `<stdbool.h>`（按项目声明的C标准使用）。
- 普通状态码可用int或具名枚举，不把“使用定长整数”扩大为禁止所有int。
- 不修改的数据使用const；标量、结构体和指针按各自含义初始化，不盲目给所有对象memset。
- 收窄及符号转换前校验范围，显式转换不能替代溢出检查；移位和中间表达式也需考虑实际类型。
- 不散布无意义数字，时间、频率、电压等常量标明单位。常量写在比较左侧为可选风格，模块内保持一致。
- 可复用第一方模块声明版本时，采用 `XXX_VERSION_MAJOR/MINOR/PATCH`；如用24位组合版本号，明确每段0～255及编码规则。第三方模块保留原版本信息。

### 5.3 控制流和错误处理

- 函数职责单一，较复杂流程提取步骤，不靠嵌套条件堆砌业务。
- 公共接口检查必要的指针、长度、枚举和状态；返回值区分成功、参数错误、忙、超时等实际情况。
- 原文“非法参数静默返回”仅适用于已说明的void接口。初始化、资源分配及关键控制失败必须可观测、可传播，不能伪装成功。
- `switch` 带default，明确非法状态的处置；有意贯穿须明确标注并通过相应编译检查。
- 底层等待具有超时或可证明的退出条件；主循环、调度器及故障停机等有意无限循环须说明目的。
- 断言用于开发期不变量，不能取代对外部输入和运行期失败的处理；关闭断言后关键保护仍然有效。

## 6. 回调、实时性与并发

### 6.1 回调与上下文

新设计的可复用接口需要多实例时，回调携带 `void *ctx`，记录对象生命周期及解绑方式。第一方单实例业务允许静态桥接，但必须声明限制及并发条件。

原文要求第三方回调带ctx，同时要求不改第三方源码。两者冲突时保持第三方接口，通过外部适配层桥接；无法提供多实例能力时明确限制，不假设加一个ctx参数就完成兼容。

### 6.2 中断及裸机轮询

板级异常和中断入口集中到 `bsp/src/bsp_isr.c`，声明放在对应头文件；实际向量符号以启动文件为准。RTOS接管的SysTick、PendSV、SVC等不得重复定义。

ISR仅完成必要的数据搬运、状态记录和通知，不进行无界等待、复杂格式化输出或长时间业务处理。共享缓冲区明确生产者、消费者及满/空策略；不能仅凭一个volatile变量认定多字段或读改写操作具有原子性。

裸机周期任务采用统一单调时基，记录单位和频率。无符号时间差可用于处理计数回绕，但须满足计时范围及调用间隔约束，不能允许多个回绕而未检查。各轮询步骤避免长时间阻塞，并定义超周期时补执行还是跳过。

### 6.3 RTOS、DMA与资源

- 线程说明优先级、栈、周期、执行预算和依赖；测量栈高水位及关键路径响应时间。
- 明确线程/ISR共享数据的同步机制，ISR只调用内核支持的ISR接口。
- 互斥、临界区及中断屏蔽具有受控持续时间，不在持锁期间执行未知阻塞操作；定义锁顺序。
- DMA缓冲区明确所有权、有效期、对齐及完成通知；平台有缓存时按其一致性要求维护。
- 动态分配并非统一禁止，但须明确允许阶段、失败处理和碎片风险；实时关键路径优先使用可界定的资源策略。

## 8. 测试与验证

| 层级 | 验证重点 |
|---|---|
| 主机单元测试 | 算法、状态机、协议解析、缓冲区边界、异常参数及回绕；隔离板级依赖 |
| 目标构建及静态检查 | 所有选定目标的编译、链接、配置、告警及资源占用 |
| 集成测试 | 模块接口、初始化失败、消息/回调、超时与恢复 |
| 板级测试 | 上电、时钟、中断、外设、实际时序、看门狗和复位恢复 |
| 产品验证 | 实际业务、异常工况、硬件/固件兼容、升级及参数兼容（按功能） |

测试文件须对应当前API和真实目录；框架及依赖可获取。记录运行命令、工作目录、基线、通过/失败/跳过数量及报告，不能以有测试文件或零用例通过代替测试完成。

主机测试不能证明真实硬件时序，编译通过不能证明板级功能正确。故障路径至少覆盖适用的超时、断线、错误输入、资源失败和复位；测试深度按产品风险和变化范围确定。

## 9. 评审、版本与发布

评审至少覆盖分层边界、API契约、异常路径、并发、资源、配置、依赖及验证结果。设计说明与实现变化同步更新；遗留问题记录负责人、风险和批准状态。

正式发布须固定源码、依赖、构建目标与配置，生成并归档：

1. 固件版本、源码完整提交、支持的硬件版本及装配变体。
2. 编译器、SDK、Pack、关键选项及实际构建命令/步骤。
3. 可烧录镜像、烧录地址、必要引导程序/参数和校验值；格式按工具选择，不要求全部格式齐备。
4. 调试符号、map、内存占用及关键测试/评审记录。
5. 变更说明、已知限制、升级与回退方法；存在持久化参数时说明格式兼容及迁移。

已发布包不覆盖，修正后使用新发布编号。用于日常构建的忽略规则不等于无需归档正式固件。发布前验证目标板实际运行行为，不仅确认镜像文件存在。

以下是对固定参考基线的静态核对，不是本次已修复或已运行通过的结果。实际项目使用前应分别解决。

| 观察 | 规范中的处理原则 |
